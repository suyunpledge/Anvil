# 工单状态机 · 契约 v1

> 这份文件是状态机的宪法。`statemachine/contract.py` 是它的代码化身——两处必须同步改。
> 引擎（`engine.py`）只允许按这里写死的数据行事，不许自己发明流程。

日期：2026-09-27　版本：v1（第一版，刻意做窄）
适用场景：**单文件 Python 修改 + 测试通过**。就这一个场景，跑通之后再抽象。

---

## 0. 这一版刻意不做的事

先说边界，免得后面越写越大：

- 不做通用多文件工单，不做跨语言；
- 不接 UI，不接 VS Code，只有命令行；
- 不做 git 提交（`allow_git_commit` 默认关；留了实现但不在链上）；
- 不做检索增强（读节点只用文件内容 + 正则搜引用，不上向量检索）；
- 不做并行、不做多模型编队（那是画像跑起来之后的衍生动作）。

对应地，本版把力气全花在**一处**：让「读 → 改 → 语法 gate → 类型 gate → 测试 gate」这条链在真实工单上闭环，并且把兼容层的静态规则变成状态机里的动态执行。

## 1. 工单长什么样

`WorkOrder`（`contract.py`）的字段。前五个是必须的，剩下的是执行参数与现场记录。

| 字段 | 含义 | 说明 |
|---|---|---|
| `wo_id` | 工单号 | 同时用作暂存目录名、运行日志名 |
| `task` | 任务描述 | 自然语言，直接进提示词；不参与任何判定 |
| `workdir` | 沙箱根 | 所有读写都被限制在这个目录内 |
| `target` | 目标文件 | 相对路径。**写操作只允许落在它上面** |
| `test_path` | 测试文件 | 相对路径。测试 gate 用它；v1 必须声明，否则测试 gate 直接判「未声明」 |
| `test_cmd` | 自定义测试命令 | 可选，覆盖默认的 `unittest discover` |
| `node` | 当前节点 | 引擎推进，模型无权改 |
| `round_no` | 修复轮次 | 每次 gate 失败 +1，超过预算就降级人审 |
| `status` | 状态 | 见第 5 节 |
| `history` | 历史尝试记录 | 一串 `Step{node, round, turn, kind, ok, tool, detail, sec}` |
| `gate_results` | gate 结果 | 每个 gate 每次运行的完整信号（含失败原因原文） |
| `violations` | 违规记录 | 越权工具、危险参数、一轮多次写等，带触发的规则号 |
| `questions` | 需要人回答的问题 | 模型反问时落这里 |
| `artifacts` | 产物 | 每轮补丁 diff、累计 diff（原文件→改后）、耗时、安全层来源 |
| `constraints` | 预算 | `max_repair_rounds` / `best_of_n` / `write_scope` / `allow_git_commit` |

工单是**唯一**的输入结构：引擎不读对话历史、不读全局状态，重启后把工单 JSON 喂回去就能接着跑（v1 还没实现 resume，但数据结构已经为此留好）。

## 2. 五个节点的契约

节点分两类：**模型节点**（要调模型）和**程序节点**（纯代码，只在 gate 系）。

### 2.1 读节点 `recon`（模型）

| 项 | 内容 |
|---|---|
| 输入 | 任务描述、沙箱目录清单、目标文件当前内容（框架确定性读取，不靠模型自己找） |
| 工具集 | `read_file` / `list_dir` / `search_code` — **没有写权限，也没有 `run_shell`** |
| 思考 | 关（`node_kind=slot`，依据 E13：选工具/抽参数关思考不掉质量，延迟从 4–8s 降到约 1s） |
| 上下文 | `num_ctx=16384` |
| 回合 | 最多 3 轮模型调用；每轮的工具结果喂回下一轮 |
| 输出 | `ContextBundle{target_source, search_hits, notes}` |
| 通过信号 | 拿到 bundle。模型可以「不调用任何工具，直接给结论」结束（空调用合法，R10） |

框架**先自己读一遍目标文件**再让模型看，这样即便模型不读文件，改节点也一定有源码可用。

### 2.2 改节点 `edit`（模型）

| 项 | 内容 |
|---|---|
| 输入 | ContextBundle、任务描述、**每轮重新读取的最新源码**、修复轮时的 gate 失败原文 |
| 工具集 | `read_file` / `apply_patch` / `search_code` — **没有 `write_file`**（依据 E15：给了它就会整文件重写） |
| 思考 | 开（`node_kind=edit`）。修复轮用 `repair`，同样开 |
| 上下文 | `num_ctx=16384` |
| 回合 | 最多 3 轮。模型只读不写时（E7 实测行为）追加一次「现在请给补丁」的提醒，仍算同一轮 |
| 输出 | `Patch{path, mode, diff, added, removed}`，写进暂存区 |
| 通过信号 | 补丁成功应用，且**只落在工单声明的目标文件上** |

写范围是硬约束：`apply_patch` 的 `path` 不是目标文件就直接拒。这条让模型**没法改测试文件把测试改绿**。

### 2.3 语法 gate `gate_syntax`（程序）

输入暂存区的目标文件，输出 `ast.parse` 的结果。通过信号 = 能解析。
失败时给出 `{type: syntax_error, line, col, message}`，并附上出错那一行的原文。

### 2.4 类型 gate `gate_type`（程序）

v1 是三件事，全部纯标准库（本机没有 mypy/pyflakes）：

1. **名称解析**：所有 `Name` 读取都要能在（局部 → 闭包 → 模块 → 内置）链上找到定义。抓的是 8B 模型最常见的错——写了不存在的函数/变量名。
2. **注解完备**：模块层与类层的函数，参数（除 `self`/`cls`）与返回值必须有类型注解。嵌套函数不要求（减少噪声）。
3. **保留性检查** + **重复定义**：见下。

通过信号 = 零 issue。issue 类型：`undefined_name` / `missing_annotation` / `duplicate_def` / `removed_symbol` / `removed_main_guard` / `unreachable_code` / `dead_string`。

后两类是**死代码检查**，由 2026-09-27 的 qwen3:8b 真机跑补进来的：模型把新实现插在函数顶部、
旧函数体不删，语法/测试全过、函数语义也对，但补丁里留着一截永不执行的旧代码。
它顺带抓到了另一类毛病：补丁把实现插进了**错的函数**（在 `add()` 里 return 了 `nums` 的均值），
错误就表现为「`nums` 未定义 + 不可达代码」。

**它明确不是 mypy**：不推断类型、不跨文件解析、不做调用元数检查。真正的类型错误最终由测试 gate 兜底。

### 2.5 测试 gate `gate_test`（程序）

在暂存区跑 `python -m unittest discover -s . -t . -p <测试文件>`，通过信号 = 进程返回 0。
`raw` 里带 `rc / tests_run / failures / errors / output`，失败时把输出尾部（截 4000 字符）喂回改节点。

两个细节是踩坑换来的：

- **工单没声明测试文件时直接判失败**，不允许空跑通过——否则「0 个测试、退出码 0」会变成一次假绿。
- 必须走 `unittest discover`：本机内嵌解释器带 `python313._pth`（隔离模式），`cwd` 与 `PYTHONPATH` 都不进 `sys.path`，直接 `python -m unittest <module>` 必然 `ModuleNotFoundError`。discover 会把 `-t` 指定的绝对目录插进 `sys.path`，因此稳定。

## 3. gate 的通过 / 失败信号长什么样

所有 gate 返回同一个结构（`GateResult`），并且**只有两个取值**的 `signal`：

```json
{
  "gate": "gate_type",
  "ok": false,
  "signal": "fail",
  "issues": [
    {"type": "undefined_name", "message": "名字 nms 未定义（未 import、未赋值、也不是内置）",
     "line": 15, "col": 8, "hint": "检查拼写，或把需要的名字 import 进来"}
  ],
  "sec": 0.002,
  "error": "",
  "raw": {"checked": true, "issue_count": 1, "removed_symbols": 0},
  "round": 1
}
```

规矩两条：框架其它部件只允许看 `ok`；`raw` 与 `issues` 是给人看的证据，**不许**解析里面的自然语言来做判断。

## 4. 失败了往哪儿退

| 失败点 | 退到 | 反馈内容 | 升级条件 |
|---|---|---|---|
| `gate_syntax` | 改节点（`repair`） | 语法错误原文 + 行号 | 同一 gate 连续失败 2 次 → 先重跑读节点 |
| `gate_type` | 改节点（`repair`） | issue 清单（类型、行号、建议） | 同一 gate 连续失败 2 次 → 先重跑读节点 |
| `gate_test` | 改节点（`repair`） | 测试输出尾部 | **同样的失败签名**出现 2 次 → 重跑读节点；说明模型没抓住要点，再改也没用 |

「连续失败 2 次先刷上下文」三个 gate 都生效（2026-09-27 补上：原来只对 gate_test 的失败签名做了，
文档写了而引擎没接线，属于「文档比实现多」的典型漏洞，已用回归测试钉住）。

另外几条不在表里但同样硬的规则：

- 修复轮总数超过 `max_repair_rounds`（默认 3）→ 终止，状态 `escalated`，交人审；
- **同一份无法应用的补丁被连续提交 2 次** → 立即终止（`escalated`）。实测 qwen2.5-coder 拿到反馈后会
  原样重发同一个错补丁，多给它轮次只是白烧时间与额度；
- 危险参数（R2）→ **当场判死**，不重试、不回炉；
- 越权工具（R1）→ 拒收该调用、退回改节点重写；同一节点内累计 2 次 → 整单安全终止；
- 模型反问 / 只给文本不给补丁 → `needs_input`，把问题原文交给人；
- 上下文超限 → `failed`，提示走检索精简而不是调大窗口。

「失败签名」= 测试输出里所有 `FAIL:` / `ERROR:` 行排序后拼起来。用它来判断「两次失败是不是同一件事」，比看通过率可靠。

## 5. 终态

| 状态 | 含义 | 落在磁盘上的后果 |
|---|---|---|
| `done` | 五节点走通、三个 gate 全过 | 暂存区验证过的文件原子替换回沙箱 |
| `needs_input` | 需要人补充信息（模型反问 / 给不出补丁） | 不改动任何文件 |
| `escalated` | 修复轮用尽，降级人审 | 不改动任何文件 |
| `failed` | 确定性失败（上下文超限 / 传输层反复失败） | 不改动任何文件 |
| `security_abort` | 触发安全边界（危险参数 / 反复越权） | 不改动任何文件 |

**只有 `done` 会落盘**。变更全程在暂存区（`.sm-work/<工单号>/`）完成，验完才 `os.replace` 原子替换；原始文件另存一份 `.sm_original_target.py`，用于对照、回滚与保留性检查。

## 6. 兼容层 12 条规则挂在哪

| 规则 | 挂载点 | 状态机怎么执行 | 验证 |
|---|---|---|---|
| R1 按节点授权工具集 | recon / edit 的请求侧 + **引擎执行前再查一次** | 越权调用拒收、记 `violations`、退回重写；重复 2 次终止 | `verify_sm_rules.py` R1 六项 |
| R2 危险参数判死 | `shell` 节点 / 任何被闸工具 | 命中即 `security_abort`，不回炉 | R2 两项 |
| R3 思考预算 | 节点 `node_kind` | edit/repair 开、recon 关 | R3 五项（读真实请求体） |
| R4 温度阶梯 | 适配层内部，引擎负责给 N | 首轮 0；模型级失败才升温 | R4 两项 |
| R5 上下文配额 | 节点 `node_type` | 按策略下发、夹到上限、超限告警 | R5 两项 |
| R6 format 与 tools 互斥 | 适配层请求体 | 引擎不发 format；请求体里永远没有它 | R6 两项 |
| R7 框架供计划、模型填槽 | 引擎与模型的两个接口 | 引擎只调 `fill_slot`，从不自己拼请求 | R7 源码断言 |
| R8 gate 是唯一真相源 | 主循环 | 模型自称「已完成」零效果；只有 gate 全过才落盘 | R8 两项 |
| R9 参数归一与校验 | 引擎执行前 | 类型/必填不合 schema 直接拒 | R9 两项 |
| R10 空调用合法 | recon / edit | 读节点空调用照常继续；改节点空调用转 `needs_input` | R10 一项 |
| R11 每次 gate 回写画像 | 引擎 | gate 与工具结果都写进能力画像 | R11 一项 |
| R12 失败必须归类 | 主循环 | 所有 kind 落在 `KINDS` 里；越权单列 | R12 两项 |

「引擎执行前再查一次」是有意的重复：适配层已经拦过一遍，但引擎不能假设适配器永远正确（换适配器、被绕过、将来接别的模型）。安全判定不能只有一处。

## 7. 首次真机运行暴露的缺口（已修补）

第一次拿真模型跑五节点，跑出了三个 gate 一个都没发现的问题：

模型为了让「名字 `main` 未定义」这个类型错误消失，**没有把 `main()` 加回来，而是把 `main()` 和 `if __name__ == "__main__":` 一起删掉了**。语法、类型、测试三个 gate 全部通过——测试文件里根本没有测 `main`，所以测绿了；类型 gate 的不存在名字错误也因为删掉调用方而消失。文件功能正确（average 实现了、测试 3/3 通过），但无关代码被静默删除。

于是类型 gate 加了保留性检查：与框架留存的原始副本对比模块层符号（顶层函数/类/常量 + `__main__` 入口守卫），原有符号消失就报 `removed_symbol` / `removed_main_guard`，退回改节点。第二次真机运行里这个检查没有再被触发——一次一行、`main()` 完好。

这条记在这里，是因为它说明一件更重要的事：**「测试通过」不等于「改对了」**。gate 的覆盖面就是状态机的信用边界，漏掉的检查迟早会被人发现。

## 8. 后续真机跑补的两个检查（同一教训的延续）

同一天拿 qwen3:8b 与 qwen2.5-coder 各跑一道同样的工单，又各扇出一个：

**qwen3:8b（wo-qwen3-8b-01）**：把新实现插在函数顶部，**旧函数体没删**——`return` 之后就挂着
一截永不执行的旧代码。语法、类型、测试三个 gate 全过（函数语义是对的），但补丁是脏的。
→ 类型 gate 加**死代码检查**（`unreachable_code` / `dead_string`）。

**qwen2.5-coder（wo-qwencoder-03）**：无 thinking 的模型不会算行号，把补丁插进了**错的函数**——
`add()` 里出现了引用 `nums` 的语句，而 `average()` 原封不动。新加的死代码检查与名称解析一起把它拦住了：
`nums 未定义` + `不可达代码`。随后它拿到反馈**重复提交同一份错补丁**，两轮后升级人审。

两个模型、两个毛病、一个共同结论：**能力越弱的模型，framework 侧的结构防线（gate）越要厚**。
模型能自己发现的问题就不叫问题；gate 的价值全在它发现不了的那部分。

## 8. 多模型：换模型只换画像

节点链与 gate 是模型无关的，模型专属的一切（工具集、思考策略、上下文配额、
能不能发 `think`、要不要从正文抠工具调用、节点轮次预算、编辑提示增补）都收在一份
`ModelProfile` 里。现役两份：`mythos`（原生通道派）、`qwen-coder`（正文 JSON 派）。

细节与实测依据见 `compatibility/画像与适配层-说明.md`；换新模型的操作清单也在那份文件里。

一句话：**安全口径（R1/R2/R9/R12）与传输层不随模型变**，变的是数据。

## 9. 从 chat-ollama 吸收的两条（2026-09-28）

对标 `sugarforever/chat-ollama`（详见 `local-model-ide/chat-ollama-技术解剖与差异化定位.html`）后，
它在「让模型安全地碰文件」上比我们细，其中两条直接并进了本版内核：

### 9.1 写操作加内容版本号（乐观并发）

原状：`apply_patch` 只靠「old_string 唯一匹配」防误改。只要文件在「模型看到」与
「补丁落盘」之间被另一条路径改过，匹配仍可能成功 → **静默覆盖**。

现做法：`read_file` 返回 `version: sha256:<64hex>`；写入前比对；不符则报冲突且不改文件。
关键细节：**版本号由引擎自动注入**（`_seen_version`），不靠模型记得传——模型的活儿已经够多了。

```
读节点/改节点读到文件 → 记下 version
改节点要写 → 引擎自动带上 expected_version
文件被旁路改过 → VersionConflict，进 violations，退回重写
```

### 9.2 路径边界真解析符号链接

原状：只做 `normpath` 字符串前缀判断。软链接（`link -> 外部目录`）在字符串上看是“在沙箱内”，
写进去就出了沙箱。

现做法：沙箱根经 `realpath` 归一；待解析路径的**已存在祖先部分**再 `realpath` 一次，
然后判越界；同时拒绝兄弟前缀混淆（`/work-other` 不被 `/work` 误判为内部）。
两条都有物理符号链接的回归用例。

### 9.3 另外两条待做（已记入动作清单）

- 搜索换 `rg` 走参数数组（`shell:false`），解决现在 Python 扫描慢且正则由模型给的问题；
- provider 错误出口统一脱敏（我们踩过 key 进日志/命令行的坑）。
