# 文件整理工单 · 契约 v1

> 这是代码类工单（`docs/工单状态机-契约-v1.md`）之外的**第二类工单**。
> 它要回答的问题不一样：代码工单问「改对了没有」，整理工单问「有没有弄丢东西」。

日期：2026-09-28　适用：本机文件按类型/规则归类（文件查找、桌面整理）
配套代码：`statemachine/tidy.py`（闸与执行）、`statemachine/tidy_engine.py`（状态机）

---

## 0. 为什么单独做这一类

用户 2026-09-28 的原话是：本地模型的优势在**安全、隐私**，像「文件查找和桌面整理」这种
简单小任务就可以改善优化。这句话决定了两件事：

**一、这类任务不该交给云端模型。** 把「你硬盘上有什么」这份清单发给云端，本身就是一次
数据外泄。交给本地模型，零外传。这是本地模型独属的优势，而这类任务恰好判断简单、
执行机械——弱模型完全够用。

**二、这类任务的风险方向和代码不一样。** 改代码错了，测试会红；整理文件错了，
文件可能就没了。所以这一版的全部设计都围绕一件事：**让不可逆的动作根本无从发生。**

---

## 1. 与代码工单的异同

| 维度 | 代码工单 | 整理工单 |
|---|---|---|
| 模型做什么 | 填两个槽：找位置、给最小补丁 | 只出一份**方案 JSON** |
| 模型能碰文件吗 | 能（但只有 `apply_patch`，且只限目标文件） | **完全不能**，工具集为空 |
| 谁执行变更 | 模型调工具，引擎执行 | 框架执行，模型只出文本 |
| 闸的位置 | 写在**后**（语法/类型/测试） | 写在**前+后**（方案闸 / 复核闸） |
| 失败代价 | 测试红，可重来 | **文件丢失，不可逆** |
| 回退对象 | 退回改节点重写补丁 | 退回规划节点重出方案 |

共用的是骨架：工单结构、`Step` / `GateResult`、回退循环、模型画像、引擎级授权、
失败分类。不共用的是判据——判据完全不同，所以分成两份契约。

---

## 2. 五节点链

```
scan（扫清单，纯程序） → plan（模型出方案） → check_gate（方案闸，程序）
        → apply（执行，程序） → verify_gate（复核闸，程序）
```

### 2.1 scan — 确定性扫描

不调模型。扫出根目录下的待整理文件清单（名字、后缀、大小、修改日期）+ 已有子目录。
可带过滤器（后缀白名单 / 文件名正则）。系统目录（`$RECYCLE.BIN`、`System Volume
Information`）与缓存目录（`node_modules`、`.git`、`AppData`、`__pycache__`）一律跳过。

模型只看扫描结果，看不到也不需要看到整个目录树的其它部分。

### 2.2 plan — 模型出方案

模型拿到：任务描述 + 文件清单 + **允许归入的目标目录白名单** + 已有子目录（提醒别乱放）。

输出格式（唯一合法形状）：

```json
{"moves": [{"action": "move", "src": "原文件名", "dst": "目标目录/新文件名", "reason": "为什么"}]}
```

解析器容忍实际会遇到的四种形态：合法 JSON 对象 / 裸 JSON 数组 / markdown 围栏 /
单引号 Python 字典。解不出就退回重出，不猜。

**关键点：模型没有工具。** 规划节点用 `adapter.ask()`（纯文本问答），不传工具表。
它唯一的输出是一段文字——想干坏事没有着力点。这条已固化成回归测试
（`test_model_is_never_given_file_tools`）。

### 2.3 check_gate — 方案闸（执行前）

逐条审，五类判据：

| 判据 | 触发 | 类型 |
|---|---|---|
| 方案非空 | `moves` 为空 | `empty_plan` |
| 动作数上限 | 超过 `max_moves`（默认 200） | `too_many_moves` |
| **禁止删除** | 出现 `delete`/`remove`/`trash`/`unlink`/`overwrite` 等 | `forbidden_delete` |
| 动作类型 | 不是 `move` | `unknown_action` |
| 源存在且在根内 | 清单里没有这个文件，或路径含 `..`/绝对路径 | `src_missing` / `src_outside` |
| 目标在根内且在授权目录内 | 越界，或放进了非白名单目录 | `dst_outside` / `dst_not_allowed` |
| 同源不重复 | 一个文件被安排移动两次 | `duplicate_src` |
| 目标不覆盖 | 目标已存在（`overwrite=False`） | `dst_exists` |

命中 `forbidden_delete` → **直接安全终止**（`security_abort`），不重试、不回炉。
与代码侧 R2 危险参数同一条口径：安全边界不给商量。

其它问题 → 退回规划节点重出，带闸的原文反馈，最多 `max_repair_rounds`（默认 2）轮。

### 2.4 apply — 执行（含逐条二次检查）

逐条移动，每条都做「目标已存在则跳过」检查。**绝不覆盖**——即使方案闸因为并发原因
漏了什么，执行层仍然拒绝覆盖。目标目录按需创建，记录实际创建了哪些。

### 2.5 verify_gate — 复核闸（执行后）

执行完必须自己证明「没弄丢东西」，四条判据：

1. **原位置核对**：原位的文件集合 == 原清单 − 已移动集合。多一个少一个都报问题。
2. **目标目录核对**：每个目标目录里的文件数不少于方案声称的数量。
3. **移动结果核对**：方案声称已移到 X 的文件，必须真在 X（`moved_file_missing`）。
4. **计数守恒**：原文件数 == 原位剩余 + 已移动。

任何一条不过 → `escalated`，交人审，并在日志里给出精确的清点结果。

## 3. v1 的硬口径

- **零删除。** `allow_delete` 写死 `False`。整理不需要删；想清理重复文件是另一个工单，
  那要人逐个确认。先把不可逆动作从工具集里拿掉——这与代码侧「编辑节点不给 `write_file`」
  是同一条思路：不靠提示词，靠结构。
- **零覆盖。** `overwrite` 写死 `False`。执行层与方案闸双重拒绝。
- **dry_run 优先。** `--mode dry_run` 是默认值。先看方案，确认了再 `--mode execute`。
- **模型不碰文件。** 规划节点没有工具；移动由框架做。
- 不做：递归整理子目录、删除、改名以外的语义动作（如按内容归档）、跨根目录搬运。
  都是"等有人真需要再做"。

## 4. 文件查找（`find`）

与整理分开：**查找是完全确定性的，不调模型、不联网。**

理由：找一个文件不需要「智能」，只需要「准」与「不外传」。把硬盘上的文件名清单
发给云端模型，本身就是一次数据外流；本地搜完全不外传。

```bash
python statemachine/cli.py find --root <目录> [--name 正则] [--content 正则] [--ext .md,.txt]
```

支持文件名正则、内容正则（只搜文本类后缀）、后缀限定；结果永远带 `truncated` 标志
（达到上限时显式告知，不假装找完了）。

模型在这类任务里的正确位置是**解释与汇总**（"我该整理哪些"），不是执行查找。

## 5. 怎么跑

```bash
# 文件查找（本地、零网络）
python statemachine/cli.py find --root "C:\Users\<你>\Desktop" --ext .pdf,.zip --max-hits 50

# 整理 —— 先出方案（默认 dry_run，不动文件）
python statemachine/cli.py tidy --root "C:\某目录" \
  --dirs "文档,图片,压缩包,表格" \
  --task "按类型整理：PDF/文档/笔记归到 文档，图片截图照片归到 图片，压缩包归到 压缩包，表格数据归到 表格。不确定的不要动。"

# 确认方案没问题，再真执行
python statemachine/cli.py tidy --root "C:\某目录" --mode execute --dirs "..." --task "..."
```

退出码：0 完成 / 3 未完成（含降级人审 / 安全终止 / 失败）。
每次运行写 `.sm-runs/<工单号>.json`，含完整方案、闸结果、逐条移动日志、清点数据。

## 6. 真机跑过的一次（2026-09-28）

样板：14 个文件的乱桌面（PDF/文档/笔记/图片/压缩包/表格/安装包混放）。

- 规划 96.3 秒出 13 个动作；方案闸 ok（0 条问题）；dry_run 不动文件 ✓
- 执行 119.1 秒：13 个文件归位，复核闸 ok，**总文件数守恒 14/14** ✓
- `安装包.exe` 模型主动没动它——"不确定的不要动"这条提示词真的起了作用

顺带记一条：模型没有出现"给同一个文件安排两个目标"或"凭空调到未授权目录"这类幻觉。
如果出现，方案闸会在执行前拦住（已有回归用例覆盖这两种）。

## 7. 变更规则

改这份契约时同步改三处：本文档、`statemachine/tidy.py` 的判据表、
`statemachine/test_tidy.py` 的断言。三者不同步，比没有契约更危险。
