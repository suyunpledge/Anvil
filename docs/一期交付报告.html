一个刻意的选择：扩展不用构建步骤

写成纯 JS 而不是 TypeScript，是因为本机网络按流量计费，一次 npm install 的下载量不该花在这种事上。代价是没有类型检查，于是补了一个 35 项的静态检查脚本（命令注册、配置键、入口、转义、无外连）来补上这道防线——它确实抓到了一个真 bug（见第 04 节）。

02

项目结构：出口只有一个

这张图里有三处是这一期特意做的"窄口"：

  • 出口只有网关一个。为了让状态机也走它（而不是绕过它直连 Ollama），网关额外开了一个 Ollama 兼容端点——因为状态机内部本来就是按 Ollama 的形状发请求的。这样画像与审计对所有调用生效，而状态机一行没改。
  • 判断权只在 gate。模型说"已完成"不产生任何效果；只有三道 gate 全过才算过。
  • 落盘权只在人。工单跑完停在 awaiting_confirm，目标文件一个字节都不动。

修复过程中自己暴露的一个设计缺陷（最值得记）

把上下文层接进链路之后，同一道题的端到端测试反而失败了。查下来是真问题：

裁剪后的上下文 221 token，而整个文件才 106 token —— 小文件上「裁剪」是净负担，而且模型看不到完整文件布局，把函数删错位了。

现在的口径改成只有真省才用：裁剪结果不小于全文的 90% 时，老老实实给全文，并把回退原因记进 artifacts.context.skipped。回归测试：test_long_context_falls_back_to_full_text。

教训：优化项上线前，要在「它不该生效的场景」也测一遍，否则优化会变成退化。

关于第 1 条的准确定性（重要区分）

加固后的 sandbox.py 做的是：清环境变量、掐断代理、隔离 HOME、限制 cwd 与超时。
它做到的是「降低测试进程带来的风险」；没做到的是「真隔离」——不阻断直连 socket、不限制该用户能访问的任意文件、不限 CPU/内存。

所以它被列为仍待解决项的第 1 优先级（见下一节的待办清单）。真隔离需要 OS 级手段（Windows：Job Object + 受限令牌；Linux：bwrap/unshare），本机当前不具备。

04

本轮修掉的 5 个缺陷（附根因）

这 5 个都是写代码过程中真实撞上的，每一个都写了根因和回归点——因为这类坑会重复出现。

#症状根因修法
1 所有 POST 回 422，报 loc:["query","request"] 文件顶部有 from __future__ import annotations，注解被变成字符串；FastAPI 拿字符串去模块全局找类型，而我把 Request 写在函数内部导入 → 全局没有该名字 → 被当成查询参数 FastAPI 的导入提到模块顶层
2 ModuleNotFoundError: No module named 'runner' 本机内嵌解释器是隔离模式（._pth），脚本所在目录不进 sys.path 显式把脚本目录 insert 进 sys.path
3 工单实际在等确认，快照却报 done snapshot() 用结果集覆盖了顶层字段，而结果里有同名 status（那是引擎判定） 底层字段改名 run_status；顶层 status 不可被覆盖 + 回归测试
4 工单跑完，审计里一条记录都没有 状态机直连 Ollama，把网关整个绕过去了——画像与审计两条承诺静默失效 加 gateway/client.py，把适配器的 transport 换成网关；网关加 Ollama 兼容端点；不静默降级
5 扩展渲染时 ReferenceError 模板里引用了未定义的变量（我改模板时漏了定义） 预拼片段；静态检查器本来就盯着这类问题，这次是它抓到的

第 4 个最值得记

它的危险不在于"审计没记录"，而在于静默失效：工单照样跑完、结果照样对，只是"所有调用都过唯一出口"这条承诺已经破了，而没有任何东西会告诉你。

所以修的时候我做了一个相反的取舍：不允许静默退回直连。网关不可达时直接报错并告诉你怎么办，只在显式设 LOCAL_LLM_VIA=direct 时才允许绕过。要排障就明着排障，不要悄悄降级。

如实列出：仍存在的问题

这一节比上一节重要。粉饰过的交接文档，会让接手人踩同样的坑。

问题性质影响与建议
扩展没在真实 VS Code 里点过 未验证 静态检查 35 项全过，但没装进编辑器。这是本期最需要补的一环，建议接手第一件事就是装上看一眼
取消不是即时的 设计取舍 协作式取消，粒度是"两个节点之间"。模型正在生成时不会立刻断（一次调用可能几十秒）。要做到立刻断需把 AbortSignal 透到 HTTP 层，属改核心
qwen2.5-coder 在"替换函数体"任务上容易写坏补丁 模型能力 它没有 thinking、不会算行号，曾把整段缩进写错（语法 gate 连拦 3 轮 → 人审）。是模型问题不是框架 bug；缓解方向是让框架提供行号锚点，而不是靠提示词
核心依赖全靠"同级目录 import" 结构债 core/ 里模块靠隐式路径互相引用；新增入口必须记得调 ensure_core_on_path()。已写进交接文档，但这是长期隐患
没有并发上限 未做 工单注册表是内存字典 + 锁，单机少量够用；真要并发跑几十个工单需要加队列与上限
网关的模型路由是硬编码 待数据 ROUTES 是一期初版（edit→qwen2.5-coder / chat→gemma4 / fallback→mythos）。等基准数字出来按数据改
上下文层的符号猜测是启发式 已知局限 先从任务描述里找标识符，找不到就取第一个未实现函数。猜错时有兜底（塞整文件）不会崩，但会浪费预算
语义归类的阈值绑定嵌入模型 标定依赖 0.62 是按 bge-m3 定的（实测命中 0.66–0.80 / 非命中 0.32–0.52）。换嵌入模型必须重标定

你说之后会用 Codex 再修正一遍。为此专门写了 CODEX-HANDOFF.md，它不是 README 的复述，而是按"接手人需要什么"组织的：

其中最要紧的是改动边界那节，因为它决定修正会不会把结构改坏：

  • core/ 是快照——在这里改业务逻辑，下次同步会被覆盖。正确做法是改上游再同步。
  • 不要把判断逻辑放进扩展。一旦扩展自己判断"改得对不对"，gate 这个唯一真相源就被拆了。
  • 不要在网关里加"顺手的功能"（缓存、重试、路由实验）。它现在的价值是"唯一出口 + 可审计"，加东西会稀释这条。

另外，核心回归的 168 项、端到端 16 项、离线 112 项都是可复跑的对照基线，改完直接比数字，不靠感觉。

07

怎么跑

接手第一优先级：真隔离（目前只是「降低风险」）

加固后的 sandbox.py 清环境变量、掐断代理、隔离 HOME、限制 cwd 与超时， 但不阻断直连 socket、不限制文件访问、不限 CPU/内存。要真正硬它， 需要接 OS 级手段：Windows 用 Job Object + 受限令牌，或改走容器 / WSL；Linux 用 bwrap / unshare。

其余待办按顺序：在真实 VS Code 里跑一遍扩展 → 跑基准数字（单次 vs best-of-5）→ 行内补全 → 多文件工单。完整清单见 CODEX-HANDOFF.md 第 4.3 节。

# 解释器：本机必须用 AutoClaw 内嵌 python（自带 fastapi/uvicorn）
$PY = "C:\Program Files\AutoClaw\resources\python\python.exe"

# 1) 起两个服务
& $PY gateway/app.py      # 127.0.0.1:8080（可加 --selfcheck 只跑自检）
& $PY service/app.py      # 127.0.0.1:8090

# 2) 离线自检（112 项 + 核心 168 项，约 10 秒，不调模型）
& $PY scripts/selftest.py --core

# 3) 端到端验收（16 项，真实 HTTP + 本地模型，约 3-5 分钟）
& $PY scripts/e2e_check.py

# 4) 扩展静态检查
node extension/tests/check.js

# 5) 打包并逐文件校验
& $PY scripts/pack.py
